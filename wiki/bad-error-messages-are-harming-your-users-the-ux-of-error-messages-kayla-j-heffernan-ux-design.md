# [Bad Error Messages Are Harming Your Users - The UX of Error Messages](https://www.kaylaheffernan.com/blog/2014/12/9/error-messages)

[Kayla Heffernan](https://www.kaylaheffernan.com/blog?author=5389bff5e4b0e8a9cc14449d)

[April 13, 2015](https://www.kaylaheffernan.com/blog/2014/12/9/error-messages)

[UX of Everyday Things](https://www.kaylaheffernan.com/blog/category/UX+of+Everyday+Things)

Research from 2009*has shown that error messages increase cortisol (the stress hormone) levels in individuals when they were interacting with computers that faced a system breakdown. Our error messages are physically harming individuals; we have a responsibility to consider the UX as to not affect our users health. This has been illustrated before by[Jennifer Aldrich](https://twitter.com/jma245)of [User Experience Rocks](http://www.userexperiencerocks.com/)before, and good error messages are particularly important as they:

*   Increase speed of use;
*   Increase users subjective satisfaction; and,
*   Reduce repeat errors and complaints

## So, how do you make good error messages?

### Do's

View fullsize

![Image 4](https://images.squarespace-cdn.com/content/v1/5389bff7e4b0a4356c05b3c4/1427708614720-3X3VZS84NDNOP9M1T9YK/image-asset.jpeg)

*   Be explicit and indicate something has gone wrong
*   Be polite
*   Include message on same screen as where the error occurred
*   Include the product or component name. This helps the user determine where the problem is
*   Make error messages as short as possible while communicating all needed information- or concise but precise
*   Explain how to fix the error
*   Use the users language
*   Use the correct combination of buttons
    *   e.g. if you say "Would you like to" the options are Yes/No not ok/cancel/retry

### Don'ts

*   Write like ‘a programmer’ - No Jargon!
*   Blame the user
*   Imply the error is users fault
    *   E.g. “illegal command”

*   Over-communicate the problem
*   Give unnecessary error messages
*   Include the word "error" in the title bar
*   Use vague generalities such as "syntax error"
*   Use words like “access denied”
*   Use all caps for any word in the error message
*   Use exclamation marks (!) in the messages
*   Give multiple reasons for the error - the user won't know what to fix
